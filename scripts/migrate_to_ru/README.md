# Перенос базы в РФ (локализация по ч. 5 ст. 18 152-ФЗ)

**Статус: подготовлено, НЕ выполнено.** Нужны решение Артёма и пароль от БД Supabase.

## Зачем

Сейчас первичный сбор персональных данных идёт сразу в Supabase, регион
`eu-west-1` (Ирландия). Ч. 5 ст. 18 152-ФЗ требует, чтобы запись,
систематизация, накопление и хранение персданных россиян при **первичном**
сборе велись в базе на территории РФ. Согласие пользователя это требование
не снимает — оно про физическое расположение базы, а не про согласие.

Реальная угроза для физлица — не штраф, а **блокировка домена по требованию
РКН**. Штраф переживается, блокировка `pingly-app.ru` убивает продукт.

Стоимость переезда растёт вместе с базой: сегодня это вечер работы и короткое
окно даунтайма, при 500 репетиторах с живым расписанием — операция, которую
страшно делать. Это единственный аргумент, который здесь важен.

## Почему НЕ полный self-hosted Supabase

Проверено 28.08.2026 на боевом VPS:

```
nproc            2
free -m          всего 1963 МБ, доступно ~938 МБ
df -h /          20 ГБ, свободно 11 ГБ
docker           не установлен
```

Полный стек Supabase — это ~10 контейнеров (Postgres, PostgREST, GoTrue,
Realtime, Storage, Kong, Studio, imgproxy, meta, analytics) и минимум 4 ГБ RAM.
**Сюда не влезет**, и попытка приведёт к OOM-kill бота.

## Почему подходит связка Postgres + PostgREST

Проверено по коду: из всего Supabase используются только `.table()` и один
`.rpc()`. Ни Auth (свои сессии на подписанных куках, `password_hash` в `users`),
ни Storage, ни Realtime, ни Edge Functions.

Значит нужен ровно тот кусок, который эти вызовы обслуживает: **PostgREST**.
Это один бинарник, ~30–60 МБ RAM. Вместе с Postgres (при скромных настройках
~200–300 МБ) укладывается в доступные 938 МБ.

**Код при этом не меняется вообще.** `supabase-py` ходит в PostgREST по HTTP;
меняются только `SUPABASE_URL` и `SUPABASE_KEY` в `.env`. Альтернатива —
managed-Postgres в РФ — потребовала бы переписать `infrastructure/
supabase_repository.py` (1040 строк) на asyncpg и платить за базу ежемесячно.

## Что нужно от Артёма перед стартом

1. **Пароль от базы Supabase** (Dashboard → Project Settings → Database →
   Connection string). Через API он не отдаётся, у меня его нет.
2. **Решение по окну даунтайма.** Нужно ~15–30 минут, когда бот остановлен.
   Лучше ночью: напоминания уходят за 2 часа до занятий, ночью их нет.
3. **Подтверждение на установку Postgres на боевой VPS.** Памяти хватает, но
   запас небольшой — это изменение боевого сервера, а не правка кода.

## Порядок

### 1. Подготовка (без даунтайма, ничего ещё не переключается)
```bash
bash scripts/migrate_to_ru/01_install.sh   # Postgres 17 + PostgREST + swap + бэкапы
```
После этого новая база живёт на сервере пустая, прод продолжает работать
на Supabase. Откат — просто не переключаться.

**Про бэкапы.** Скрипт заводит systemd-таймер с ежедневным `pg_dump` в
`/var/backups/pingly` и хранением две недели. Это не украшение: в уведомлении
в Роскомнадзор заявлено «резервное копирование базы данных», а на Supabase оно
было встроенным. Без своего таймера после переезда заявленная мера защиты
просто перестала бы существовать.

### 2. Проверка схемы
Прогнать `migrations/001..023_*.sql` по порядку в новую базу и убедиться,
что структура совпадает с боевой.

### 3. Окно даунтайма
```bash
systemctl stop pingly
bash scripts/migrate_to_ru/02_dump_restore.sh   # спросит пароль Supabase
# правка .env: SUPABASE_URL=http://127.0.0.1:3000, SUPABASE_KEY=<новый anon JWT>
systemctl start pingly
```

### 4. Проверка после переключения
- `/health` отвечает;
- вход по паролю работает;
- `/tutor` показывает расписание и учеников;
- напоминание уходит (проверить на тестовом занятии);
- `POST /api/track` пишет события.

### 5. Только после успешной проверки
Удалить данные из Supabase и **обновить п. 7 Политики конфиденциальности**
(`web/templates/legal_privacy.html`) — убрать абзац про Ирландию.
Пока данные там, абзац должен оставаться: недостоверная политика хуже
неудобной правды.

## Про JWT

`supabase-py` шлёт `Authorization: Bearer <ключ>`, а ключ Supabase — это JWT
с claim `role: anon`. PostgREST проверяет подпись своим `PGRST_JWT_SECRET`
и подставляет роль из claim. Поэтому переезд = сгенерировать свой JWT
с `role: anon`, подписать его новым секретом и положить в `SUPABASE_KEY`.
Скрипт `01_install.sh` генерирует и секрет, и ключ.

RLS-политики переезжают вместе со схемой (миграции 002/006/022), роль `anon`
создаётся скриптом — поведение доступа не меняется.
